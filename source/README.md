# Remibuds 1.6 — Android update

Remibuds ("reminder buds") is a private, offline routine/reminder app for medicine and prescribed care, water, meals, walks, plans, custom activities and one-time to-dos. This update keeps the original `app.dailycare` package and storage key. Version name 1.6, version code 7, minimum Android 8/API 26, target API 36. It is signed with a fresh debug keystore generated for this build; install it as a clean install (uninstall the previous app first — no records are migrated). There is no account, server, sync, analytics, advertising or paid service. Production has no sample records.

## What is new in 1.6

This build fixes the three behaviours the user reported broken on 1.5, diagnosed from his screenshots: the reminder did not ring until he tapped into the app, the app still stopped on return from Settings/other apps, and the permission screens said everything was allowed while one switch stayed off.

Alarm rings at the set time: a new foreground service (`RingService`) starts from the reminder-fire path whenever ring mode is on. It loops the chosen alarm tone on the alarm stream with vibration, with a 10-minute cap, and stops when the user acts (tap, notification action, dismiss, snooze or record) or the cap elapses. A shared static guard (`RingSound`) guarantees the activity's `AlarmPlayer` and the service can never sound at the same time: the player stops the service first, and the service never starts while the player is ringing. The full-screen intent and the activity path stay the primary reminder screen; the service is the sound guarantee underneath. Starting the service from an exact-alarm trigger is a documented exemption from the Android 12+ background foreground-service start restriction, and the start is wrapped so a refusal falls back to a plain posted notification — the reminder is always visible.

Notification actions: ring-mode notifications carry "Mark taken" and "Snooze" buttons. They open the app carrying the reminder key plus a `careAuto` extra ("record"/"snooze"). The page applies the action once through the single existing record/snooze logic, only when the reminder card is found and focused; if the card is not found, nothing is applied and a toast says so. Shared-reminder cards never auto-apply (members are marked explicitly on the card, per the original brief). The plain tap keeps opening the card focused without applying anything. A ring-service start failure is recorded and shown in Settings → About.

Full-screen permission: the Settings button now opens the exact switch on Android 14+ (`ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` with the app package) instead of the generic App info page, where everything looked allowed while the switch stayed off. The ring warning names the switch: "Turn on 'Full-screen notifications' for Remibuds on the screen that opens."

Crash, round 2: every return-to-app path was re-audited (lifecycle, WebView callbacks, file chooser, permission flows, all 1.5-new code). Real defects fixed: `shouldInterceptRequest` could throw to the framework; `onActivityResult` left a stale pending backup/CSV state on every outcome; the WebViewClient/Chrome callbacks and lifecycle entries were not all guarded. Every lifecycle entry point is now wrapped so an unexpected `Throwable` is recorded via `CrashReports.record` instead of stopping the app. The crash capture and About report UI are unchanged. See the review doc for the per-defect list and the honest statement of what still cannot be proven without the user's problem report. No payment-gateway integration was added (still deferred).

## What is new in 1.5

This build hardens the three behaviours the user reported broken on 1.4 with ring mode on and all permissions allowed: tapping a reminder notification did nothing (the app did not open on the reminder), the reminder did not ring, and donate still showed the Copy UPI ID fallback instead of the payment-app chooser.

Notification tap: the tap PendingIntent now carries a unique request code per notification key (a stable hash of the key), so one reminder's tap can never clobber another's. The launch key is held in a pending field that reading never consumes: `onCreate` and `onNewIntent` store it, the page re-attempts focusing the reminder card after every render until the card is found and focused, and only then reports the key handled, which clears it. Ringing is started from `onCreate`, `onNewIntent` and `onResume` through one idempotent path that consumes the ring flag once. If a chosen tone fails while preparing (unreadable or corrupt file), the player retries once with a fresh player on the system default alarm tone instead of staying silent; if that also fails it stays silent rather than crashing. Settings now warns plainly when ring mode is on but notifications, precise timing, or full-screen display is blocked, with a button to the right phone settings screen. The default sound mode is unchanged ("Notification only").

Donate chooser: the gate no longer trusts a single resolver lookup. It queries resolvers, then attempts the chooser anyway inside try/catch, and only a thrown attempt falls back to the Copy UPI ID sheet. The exact verified UPI payload (payee pre-filled, no amount), the "Choose an app to pay with" title, the `<queries>` declarations and the no-package-pinning rule are unchanged; every donate entry point still routes through the single native `donate()` bridge. No payment-gateway integration was added (still deferred).

Diagnostics (new, Settings → About only): the last donate attempt is recorded (payment apps found, whether the chooser was attempted, and any thrown error) and shown as a "Last donate check" line with View/Copy. Every posted notification is recorded (key, time, ring flag), every launch carrying a notification key is recorded, and the page marking the card reached is recorded — shown as a "Last reminder launch" line (notification posted at <time>, app opened via notification yes/no, reminder card reached yes/no). If the card was never reached, the line says so. No raw stack traces appear on the main screens. See the review doc for the full audit trail and what still needs a real phone to prove.

## What is new in 1.4

Crash hardening (the top priority for this build): every entry point that runs when the app returns from a phone settings/permission screen — activity lifecycle, receivers, the JavaScript bridge, the alarm player, tone lookup and the reminder planner — was audited against hostile inputs (empty/corrupt stored state, denied permissions, missing or unreadable tone files, null alarm URIs). Real defects found and fixed: the alarm-tone cursor was read on the UI thread and closed only on the happy path (now closed in `finally`, capped at 500 rows, and the work is guarded); `AlarmPlayer` used a blocking synchronous `prepare()` on the main thread (now `prepareAsync` with an error listener and a fallback to the system default alarm tone); `Reminders.parseState` could hand the planner a state with wrong-typed collections (now every collection is validated and replaced with an empty one when corrupt); every lifecycle/receiver/bridge entry point now catches `Throwable` so a single bad value cannot kill the app. A crash-capture mechanism was also added: a default uncaught-exception handler, installed at activity start and from receivers, appends the full stack trace, thread and timestamp to a small file (last 3 reports kept) and then chains to the previous handler, so a crash still surfaces. If a report exists, Settings/About shows "Last problem report" with the first line and View/Copy actions so the report can be sent to the developer. The capture is diagnostics, not a fix by itself — see the review doc for the honest statement about what could and could not be proven without a logcat.

Donate chooser: the manifest now declares a `<queries>` element (UPI `VIEW` intents and the Instagram `https` intent). On Android 11+ package visibility otherwise hides implicit-intent resolvers, so the chooser could silently fall back to the copy sheet even with payment apps installed. Every donate entry point still routes through the single native `donate()` bridge with the exact verified UPI payload (payee pre-filled, no amount parameter — the donor enters only the amount in their chosen UPI app) and the chooser title "Choose an app to pay with". Card/net-banking options cannot appear from a UPI link; a payment-gateway checkout page is deferred to a later version and is NOT in this build.

Reminder sound list: the tone list now shows a small list first — "Default alarm tone" plus the first 4 system tones — with "Show more"/"Show less" for the full list, and "Choose custom audio…" below the list. Every tone row has a play/pause preview button (one preview at a time; preview stops on selecting a tone, leaving Settings, activity pause, a real ring starting, or tapping pause). The real on-device list comes from RingtoneManager.

Archive and delete: history records now always carry their own name/type snapshot at creation (older records are backfilled from the routine at read time without rewriting history), so history survives the routine being deleted. An archived routine's detail view offers "Delete routine" with a confirm dialog ("This deletes the routine and its future reminders. Its history stays as a permanent log."). Deleting removes only the routine definition, its group memberships and its snoozes — never its logs — stops future reminders, and Undo on past records keeps working.

CSV export: Settings gains "Export history (CSV)" — export all data, or pick a From/To date range (From defaults to the earliest record date, with "Your history starts <date>" shown). Columns: Date, Scheduled time, Name, Kind/Type, Status, Recorded at, Entered afterwards, Undone; proper CSV escaping; undone rows read "Undone (does not count)"; an empty range exports headers only. Files are written through the existing document-creation flow as `text/csv` (`remibuds-history-<from>-to-<to>.csv`, or `remibuds-history-all.csv`). The JSON backup/restore is unchanged.

## State and update behavior

The existing `daily-care-personal-v1` storage key and occurrence IDs are retained. Data schema migration preserves old routines and reports; legacy medicine becomes Tablet, with 12-hour format as default. No existing logs are invented or automatically deleted. This 1.5 build uses a fresh debug signature, so it cannot install over the previous app as an update — uninstall first; records from the previous install are not carried over. The keystore is not in this source archive. Same-key/package verification is static; actual installed upgrade retention remains unverified.

Every installation stores its own routines, groups, reports, correction trail, snoozes and settings. No shared reminder stream exists. Multiple people sharing one Android profile are not separated by accounts. Export/restore is manual and unencrypted under the user's control; restore validates the entire file before replacing data, and disables reminders. Delete removes local app records and cancels native reminders. No automatic backup is promised; device loss/data clearing/uninstall can erase records.

Failed device-storage writes roll back in-memory changes to the last durable state, abort success messages and leave an error visible. Records must not appear successfully saved after a rejected write.

## Dates, amounts and schedules

Internal scheduled times are 24-hour strings. Explicit hour/minute/AM–PM controls default to 12-hour; Settings changes display format without changing occurrence identity or alarm instant.12 AM is midnight;12 PM is noon. Custom Unicode titles are used as notification titles.

Daily routine counts refer to scheduled occurrences and scheduled date, not tablets. History is browsed by the reported action date and shows the original scheduled date/time separately from the reported and entry-created timestamps. Late to-dos keep their original due identity; completing one today keeps it in today's progress until the next day. Untimed to-dos never schedule alarms.

Schedule revisions preserve targets for future historical dates. Existing old logs retain their recorded scheduled time. Unknown historical targets from edits before this update cannot be reconstructed and are not fabricated. If a medicine already has any report today (including skipped or undone), a changed type/time/day/start schedule starts the next day, preserving today's identity rather than offering an unintended extra dose. Archive and reminder-off cancel immediately. Group membership assigns existing scheduled occurrences explicitly; it does not alter a medicine's schedule. Same-time members share a reminder and retain separate reports. Batch recording affects only selected unrecorded members; batch Undo reverses only its new records.

Amounts are optional user-entered prescription information, separate from daily event counts. Tablet/capsule/injection count fields accept numbers; injection volume/dose is never invented. Gel/patch need no quantity. Additional medicine actions can be separately reported, with no recommendation to take them.

Schedules follow device local wall-clock time, not an elapsed-hour treatment interval. Relevant timezone changes pause native planning until timing is reviewed; historical timestamps remain exact instants. DST repeated/nonexistent local times follow platform date-library behavior; travel/DST phone testing is unverified. Today advances at midnight/resume. Snooze preserves the original occurrence even across midnight; recording/skipping cancels that occurrence's future reminders. Undo does not issue an immediate medicine reminder.

## Native notifications

Android AlarmManager/receivers own delivery, independent of WebView JavaScript and a permanently running process. Exact access is checked; when allowed, exact-while-idle scheduling is used. Without it, inexact scheduling is used and readiness remains incomplete. The normal channel is HIGH importance with sound and PUBLIC lock-screen visibility. Reminder notifications carry a full-screen intent that opens the exact occurrence/group card, and the activity shows over the lock screen when launched that way. Whether the full-screen display appears depends on Android granting the full-screen-intent permission (Android 14+ shows it as a special app-access setting, reported in Settings as "Full-screen display"); without the grant, the reminder still posts as a high-importance heads-up notification. No permanent overlay window or foreground service is used. Android/user settings retain control of sound, heads-up, privacy, DND and suppression. No app can alert while the phone is fully powered off.

The planner retains valid delayed pending alerts across resume/save, distinguishes immutable intent data identities, marks delivery attempts in a ledger, cancels obsolete/recorded/skipped/snoozed/archived alarms, and renews with a daily maintenance alarm. Native receivers restore plans on restart/time changes and permission-access changes. Timed one-off to-dos can repeat until done; medicine reminders never repeat indefinitely. Notification taps carry the exact occurrence/group identity to the matching card. When "Ring + notification" is chosen, the tap intent also carries a ring flag: the full-screen target loops the chosen sound on the alarm stream with vibration until the user dismisses, snoozes or records the occurrence (or closes the detail, or the activity finishes). Notification-only mode behaves exactly as before.

Settings separately reports app notification permission, channel sound/banners, exact-alarm access, battery exemption, lock-screen guidance and full-screen display access. Silent/lowered channels are not represented as ready. OEM/global lock-screen restrictions that cannot be queried are labeled as requiring a settings check. Force-stop prevents alerts until reopening; Doze can delay even requested 5-minute snoozes. Before-first-unlock reboot delivery is not supported through Direct Boot.
